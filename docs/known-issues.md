# 알려진 문제와 제약

[프로젝트 시작 안내](../README.md) · [FMS](../fms_server/README.md)

FMS 쪽 제약을 모았다. 로봇 클라이언트 제약은 AMR-simulator README/CLAUDE.md 에 있다. 성능·오차 수치는 개발 당시의 관측값이다.

## 경로와 다중 로봇

- 동적 장애물은 센서 범위 안에서만 인식한다. 두 갈림길이 모두 막히면 과거 장애물을 기억하지 못해 경로를 번갈아 고르는 현상이 남아 있다. 장애물 기억과 시간 감쇠가 필요하다.
- 로봇끼리 서로를 장애물로 인식하거나 물리 충돌을 계산하지 않는다. 로봇마다 별도 물리 월드를 사용한다.
- PSO 경로 다듬기는 위 두 문제를 해결하지 않는다. 경유점 개수와 최종 목표를 유지하는 정적 경로 보정이다.
- 맵별 이동 정원과 점유 존 통과 예약은 [교통 제어](traffic.md)를 따른다. 존 밖의 전체 경로 예약은 제공하지 않는다. 교착은 감지해 알리지만 자동 해소는 탑승 전 도착 층 예약 회수뿐이다 — 대기 node·점유 존 허가가 얽힌 교착은 운영자가 풀어야 한다 ([교통 제어](traffic.md)). 자동 충전은 [충전과 대기 위치](charging.md). 존 내부 작업 목적지는 지원하지 않는다.

## FMS와 승강기

- 파일 저장소와 프로세스 내부 락을 쓰므로 다중 worker 운용을 지원하지 않는다.
- 로봇의 수신 여부가 불명확한 assigned 작업은 자동 재게시하지 않는다. 작업 중복을 피하기 위해 예약을 유지한다.
- 도킹·주차·구역 편집 시 실제 로봇 크기와 공간 여유는 사용자가 확인해야 한다. 맵 셀 검사만으로 도킹 접근 경로 전체를 보장하지 않는다.
- 승강기 실패·취소 후 칸 안의 로봇은 자동으로 꺼내지 않는다. 임대를 유지하고 "확인 필요"로 표시하며 운영자가 복구 API 로 하차시킨다 ([승강기](elevators.md)). 탑승한 뒤의 장애에는 예비 전환을 하지 않는다.
- 층별 문 방향이 다른 승강기는 현재 전진 탑승·후진 하차 방식으로 사용할 수 없다.
- 승강기 선택용 0.25 m 비교 격자는 로봇 폭을 반영한 실제 로봇 A*와 다르다.
- 승하차 중 사람·장애물과 승강기 안전 인터록은 구현하지 않았다.

## 운영 기능

- 경로 교차 예고는 로봇이 보고한 경로 예측에 기대는 알림이다. 자동 일시정지를 켜도 충돌 방지 수단이 아니다.
- 로봇 선택은 우선순위 순 greedy 다. 전체 최적 할당이 아니므로 작업이 몰리면 먼 로봇이 가기도 한다.
- 인증을 켜도 API 키는 평문 HTTP 로 오간다. FMS 앞에 TLS 를 둬야 한다. 브로커 인증은 별도다.
- webhook 은 같은 이벤트를 두 번 보낼 수 있다 (수신 쪽에서 이벤트 `id` 로 거른다). 8번 실패하면 버린다.
- KPI·알림은 이벤트 로그 보존 기간(기본 30일) 안의 값만 본다.
- 적재 상태 대조(`cargo_mismatch`)는 `State.loads` 를 보고하는 로봇만 한다. 그 밖에는 장부만 믿는다.
- 감속 구역은 로봇 클라이언트가 지원해야 적용된다. FMS 는 지원 여부를 확인하지 않는다.
