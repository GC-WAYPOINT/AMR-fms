# 픽업스테이션 zone·node 설계

> 상태: **구현함**. 사용법은 [FMS 안내](../fms_server/README.md#픽업스테이션)에 있다.
> 택배(LastGate 보관소 배송)·물품 장부·트레이 상태 추적은 이 리포에서 뺐다 (makerton 리포에만 있다).
> 이 문서는 맵 위의 픽업스테이션(구역 + 픽업 지점 + 반납 지점) 구조만 다룬다.

## 1. 구성

픽업스테이션 하나는 **표시용 pickup zone 1개 + 픽업 node 1개 + 반납 node 1개**다.

```text
  ┌──── 표시용 pickup zone (적재 장치·컨베이어) ────┐
  └──────┬───────────────────────────────┬─────────┘
         ● 픽업 node (트레이 적재)        ● 반납 node (빈 트레이 반납)
```

| 항목 | 내용 |
|---|---|
| zone의 역할 | 적재 장치·컨베이어가 있는 영역을 사용자에게 보여준다 |
| 픽업 node | 로봇이 지정 자세로 도착해 PICK 을 실행하는 작업 지점 (`type: pickup`) |
| 반납 node | 로봇이 빈 트레이를 내려놓는 지점 (`type: tray_return`). 필수 |
| node 위치 | zone 내부 또는 인접한 외부 |

## 2. zone과 node의 의미

- zone 진입·통과·이탈로 픽업을 시작하지 않는다. `pickup` 작업이 있어야 node에서 PICK을 실행한다.
- zone은 주행금지·감속·자동 도킹·장치 제어·물리 충돌 영역으로 사용하지 않는다.
- 장치가 실제로 통로를 막는다면 원본 점유 맵 또는 별도 주행금지구역으로 표현한다.
  표시용 zone을 그리는 것만으로 장치의 충돌 형상이 생성되지는 않는다.
- node는 점 좌표와 방향 `theta`를 가진다. 화면에서는 방향 화살표로 표시한다.
- zone과 node는 같은 맵에 속하며 1:1:1로 연결한다. 독립 생성·삭제로 고아 node를 만들지 않는다.
- zone 밖 node도 허용한다. 임의의 인접 거리 상한으로 거절하지 않고,
  편집 화면에서 연결선을 표시해 장치와 인접한 위치인지 사용자가 확인하게 한다.

## 3. 식별자와 저장

- 불변 스테이션 식별자로 `PS-<UUID>`를 사용한다. pickup zone의 `zone_id`와 같다.
- 두 node는 site `locations.json`의 named location으로 저장하고 `zone_id`를 가진다.
- 스테이션 참조는 `{site_id, map_id, zone_id}`다. 이름은 표시용이며 식별자가 아니다.
- 같은 zone에 pickup location 두 개를 연결하거나 node 없이 zone만 등록하는 요청은 거절한다.
- 작업의 `OrderNode.node_id`는 실행할 때 생성되는 노드 ID다. 맵에 저장하는 픽업 지점의 식별자와 구별한다.

```text
맵 버전 annotations.json
  zones[]: {zone_id: "PS-…", type: "pickup", name, polygon}

site locations.json
  "스테이션 A":      {map_id, x, y, theta, type: "pickup",      zone_id: "PS-…", ...}
  "스테이션 A 반납": {map_id, x, y, theta, type: "tray_return", zone_id: "PS-…", ...}
```

## 4. 생성·편집·검증

1. 맵의 **＋ → 픽업스테이션**에서 사각형 zone을 그린다.
2. 같은 맵에서 픽업 지점, 이어서 반납 지점의 위치를 클릭하고 방향을 지정한다. zone 밖도 선택할 수 있다.
3. 이름·영역·node 방향을 미리 본 뒤 한 번에 저장한다.

검증:

- zone의 유효 사각형·맵 범위, node의 유한 좌표·유효 각도·동일 맵·FREE 셀을 검사한다.
- UNKNOWN·맵 밖·주행금지 위치의 node는 거절한다. **zone 내부 포함 여부는 거절 조건이 아니다.**
- FREE 셀은 로봇이 도달 가능하다는 충분조건이 아니다. 경로·다른 로봇까지 고려한 도달 가능성은 보장하지 않는다.
- 두 node가 같은 셀이면 거절하고, 1 m 미만이면 경고한다 (로봇 여러 대 운영 시 겹침).
- 이름 중복과 1:1 연결 위반을 거절한다.
- zone 변경은 기존 맵 버전 체계에 따라 새 버전을 만든다. pickup을 장애물로 굽지는 않는다.
- node 자세 변경은 location 수정으로 처리한다. 이미 발행한 작업의 좌표 스냅샷은 유지한다.
- 스테이션을 참조하는 프리셋·미완료 작업이 있으면 삭제를 거절한다. 진행 중 작업이 참조하는 node의 이동도 거절한다.
  단순 이름 변경은 불변 참조(`zone_id`)를 유지한다.
- 일반 zone/location API로 pickup·tray_return을 부분 생성·삭제하거나 다른 타입으로 바꾸는 우회를 막는다.

반납 node 이름은 `{스테이션 이름} 반납`으로 자동 생성하고, 스테이션(픽업 node) 이름을 바꾸면 같은 처리에서 함께 바꾼다.

## 5. 저장 일관성

맵 버전과 `locations.json`은 별도 파일이므로 락만으로 프로세스 중단 시 원자성이 보장되지는 않는다.
`_EDIT_LOCK -> LocationStore._lock` 순서를 유지한다. 목록 API는 활성 맵 구역과 `locations.json`을 대조해
한쪽만 남은 스테이션을 `status=broken` 과 사유로 보여주고, 편집은 막고 삭제로 정리하게 한다.
반납 node 가 없는 스테이션도 `broken` 이며, 이 경우만 **반납 지점 추가** 편집을 허용한다.

`ZoneType._missing_` 은 알 수 없는 종류를 PROHIBIT 로 처리한다. `common/` 과 AMR-simulator `viewer/common/` 사본을
함께 갱신해 pickup 이 진입금지로 변하지 않게 한다.

## 6. 남은 과제

- node 임대: 로봇 여러 대가 같은 픽업·반납 node 에 겹치지 않게 하는 예약은 없다.
- 일반 작업의 `pickup` 명령은 스테이션 참조를 강제하지 않는다.
