# 충전과 대기 위치, 배정 순서, 예약 실행

[프로젝트 시작 안내](../README.md) · [FMS](../fms_server/README.md) · [운영 제어](operations.md)

FMS 가 로봇과 작업을 고르는 규칙과, 작업이 없는 로봇을 다루는 자동화를 설명한다.

## 작업 순서: 우선순위·시작 시각·마감

게시판 작업은 **우선순위가 높은 것부터**, 같으면 게시 순으로 배정한다.

| 필드 | 의미 |
|---|---|
| `priority` | -100 ~ 100, 기본 0. 클수록 먼저. pending 일 때 `PATCH /sites/{site}/jobs/{id} {priority}` 로 바꾼다 |
| `not_before` | 이 시각(ISO 8601) 전에는 배정하지 않는다. 대기 이유 "예약 시각 전" |
| `deadline` | 마감. 넘겨도 **실패 처리하지 않는다.** `job.deadline_missed` 이벤트와 알림만 남는다 |
| `robot_group` | 이 그룹 로봇에만 배정 |

프리셋 게시(`.../presets/{id}/publish`)와 작업 생성(`POST .../jobs`) 본문에 넣는다. 시간대가 없는 시각은 UTC 로 본다.

## 로봇 선택: 비용 순위

작업 하나에 대해 후보 로봇을 비용이 낮은 순으로 시도한다 (`fms_server/assign.py`).

- 같은 맵: 첫 목적지까지의 주행 거리 (0.25 m 격자, `route.path_distances`).
- 다른 층: 승강기 환승 한 번당 60 m 벌점 + 가장 가까운 승강장까지 거리.
- 배터리 1 % 부족당 0.2 m 가산. 동점은 로봇 ID 순.
- 제외: 점검 중, 그룹 불일치, 지원하지 않는 액션(Factsheet 보고 로봇만), 자동 충전이 켜져 있을 때 `min_job_charge` 미만.

전체 최적 할당은 하지 않는다. 우선순위 순으로 작업을 하나씩 가장 가까운 로봇에 준다 (greedy).
거리는 로봇 폭을 반영하지 않는 비교값이다. 실제 경로는 로봇이 계획한다. 최종 가용성은 `dispatch` 가 다시 검사한다.

## 로봇 그룹

- 로봇: 로봇 화면의 "그룹" 또는 `PUT /sites/{site}/robots/{id} {groups: [...]}`.
- 작업: `robot_group` 이 있으면 그 그룹 로봇만 후보다.
- 충전소·대기 위치: 운영 제어 화면의 "그룹" 또는 `PUT /sites/{site}/locations/{name} {groups: [...]}`. 그룹이 비었거나 로봇 그룹과 겹칠 때만 그 로봇이 쓴다.

## 자동 충전

정책은 현장마다 `sites/{site}/charging.json`. **운영 제어** 화면 또는 `GET/PUT /api/v1/sites/{site}/charging`. 기본은 꺼져 있고, 꺼져 있으면 이전 동작 그대로다 (배터리 0 % 만 배정 거절).

| 항목 | 기본 | 의미 |
|---|---|---|
| `enabled` | false | 자동 충전 |
| `low` | 25 | 이 미만이면 충전하러 보낸다 (%) |
| `critical` | 10 | 이 미만이면 알림 |
| `release` | 60 | 도킹 `min_charge`: 이만큼 차야 다음 작업을 받는다 |
| `min_job_charge` | 20 | 이 미만인 로봇에는 일반 작업을 배정하지 않는다 (`enabled` 일 때만) |
| `opportunity` | false | 유휴 시간에 미리 충전 |
| `idle_after` | 60 | 미리 충전을 시작할 유휴 시간 (초) |
| `staging` | `{enabled:false, idle_after:60}` | 유휴 로봇을 주차 지점으로 복귀 |

`critical <= low < release`, `min_job_charge < release` 여야 한다.

동작 (1초마다, `fms_server/battery.py`):

- 대상은 작업·배송 예약이 없는 가용 로봇이다. 점검 중이거나 정지·대피 중인 로봇은 보내지 않는다.
- 배터리가 낮은 로봇부터 충전소를 고른다. 같은 층을 먼저, 그 안에서는 주행 거리 순.
- 충전소 = 용도가 "충전소"이고 맵 `chargers.json` 의 물리 충전기와 위치·방향이 맞는 목적지. 진입 지점이 막힌 곳, 다른 로봇이 서 있는 곳, 다른 작업이 향하는 곳은 고르지 않는다.
- `docking` 명령의 **시스템 작업**을 만들어 바로 배정한다 (`Job.system = "charge"`). 다른 층 충전소면 승강기를 탄다.
- 빈 충전소가 없으면 `charge.no_charger` 이벤트만 남긴다 (같은 이유는 한 번만). 배정에 실패한 로봇은 60초 뒤 다시 시도한다.

보관소 배송의 마지막 도킹(`locker.py`)도 같은 충전소 선택(`charger_pool.py`)을 쓴다. 서로 같은 충전소를 고르지 않는다.

## 유휴 대기 위치 복귀 (staging)

`staging.enabled` 이면 `idle_after` 초 이상 유휴이고 충전소·주차 지점에 있지 않은 로봇을 같은 층의 가장 가까운 빈 **주차 지점**으로 보낸다 (`Job.system = "staging"`).

- 주차 지점 = 목적지 용도 "주차 지점". 진입 직선(0.6 m)을 낼 공간이 있으면 `parking`, 없으면 단순 이동으로 간다.
- **선점**: 일반 작업의 후보가 없는데 대기 위치로 가는 중인 로봇이 있으면 그 시스템 작업을 취소한다. 취소가 확인되면 다음 tick 에 일반 작업을 배정한다.
- 교통 제어가 "대기 node 옆에 유휴 로봇이 서 있어 못 간다"고 판단하면 그 로봇을 즉시 대기 위치로 보낸다 (비켜주기, [교통 제어](traffic.md)).

게시판은 시스템 작업을 접어 둔다. "시스템 작업 표시"로 펼친다.

## 예약 실행

프리셋 화면의 "예약 실행" 또는 `/api/v1/sites/{site}/schedules` (GET·POST, `/{id}` PUT·DELETE). `sites/{site}/schedules.json` 에 저장한다.

```json
{"name": "아침 순회", "preset_id": "…", "days": [0, 1, 2, 3, 4], "time": "09:00",
 "priority": 0, "robot_group": null, "enabled": true}
```

- `time`(HH:MM, **서버 로컬 시간**)과 `interval_s`(10초 이상) 중 하나만 준다. `days` 는 0(월) ~ 6(일), 없으면 매일.
- 때가 되면 프리셋을 게시판에 올린다. 배정은 평소 규칙을 따른다.
- `last_run` 을 먼저 저장하고 게시하므로 재시작해도 같은 회차를 두 번 실행하지 않는다.
- 서버가 꺼져 있던 동안 놓친 실행은 건너뛴다 (정시에서 90초가 지나면 그 회차는 버린다). 간격 예약은 만든 시점부터 센다.
- 게시에 실패하면(프리셋 삭제 등) 그 회차는 다시 시도하지 않고 `last_error` 에 남긴다.
